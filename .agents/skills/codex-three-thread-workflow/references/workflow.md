# Codex 三线程交付工作流

本流程把复杂任务分为三类上下文：主线程做决策，执行线程改文件，验证线程独立检查。目标不是增加步骤，而是把责任、事实和噪声隔开，使交付可控、可复现、可回滚。

## 1. 先判断是否值得拆分

满足以下全部条件时，留在一个线程中完成并自检：

- 目标和范围已经明确；
- 改动很小、低风险，通常集中在一个局部；
- 不需要大量探索、长日志或多轮排障；
- 验证快速且结论清楚；
- 独立审查不会显著提高把握。

视频给出的快速判断是：如果目标、改动和验收能在一个屏幕里看清，且大约 15 分钟内能够讲清并完成，通常不拆；如果需要不断向上翻找先前决定，就该拆。这是启发式而非硬阈值，风险、权限和不确定性优先。

出现任一强信号，或同时出现两个普通信号时，启用三线程：

- 涉及多个模块、数据边界、迁移、权限、安全或不可逆操作；
- 需求仍需权衡，实施过程中不应顺便改变产品决定；
- 探索、构建、测试或排障会产生大量中间输出；
- 实施和验收需要不同视角，存在“自己证明自己正确”的风险；
- 工作可以拆成独立的读多写少子任务并行；
- 任务预计跨较长时间、多个检查点或多次上下文压缩。

只需要独立验证但实施很小，可以使用“主线程 + 验证线程”；不要为了凑齐三个角色而创建空线程。单线程快速路径中，主线程就是唯一写入者和自检者：完成最小改动、检查精确 diff、运行相称验证并直接交付，跳过阶段 B 至 E 的代理交接。

## 2. 三个角色的职责边界

### 主线程 / `delivery_coordinator`

负责：

- 定义目标、范围、优先级、约束和验收标准；
- 识别需要用户决定或授权的事项；
- 记录基线、分配任务、控制写入顺序；
- 根据证据接受、拒绝或要求修复候选结果；
- 输出最终交付说明。

主线程应像控制台，任何时候都能回答：当前目标是什么、已经完成什么、证据在哪里、下一步交给谁。

不负责：

- 承载冗长探索记录、完整构建日志或逐条排障过程；
- 在执行线程工作时同时修改同一工作树；
- 用“看起来完成了”代替验收。

### 执行线程 / `delivery_executor`

负责：

- 阅读任务简报和适用规则，确认工作目录与 Git 状态；
- 在范围内做最小且完整的改动；
- 运行与风险相称的检查；
- 返回改动清单、命令结果、证据、假设和剩余风险。

不负责：

- 改变目标、扩大范围或替用户作新的产品决策；
- 覆盖用户已有改动、清理不相关文件或修改外部只读数据；
- 未经明确要求提交、推送、合并或改写 Git 历史；
- 把“测试未运行”写成“测试通过”。

### 验证线程 / `delivery_verifier`

负责：

- 从冻结的候选状态和验收标准出发独立检查；
- 阅读真实 diff、相关代码和测试结果，必要时复跑安全检查；
- 查找正确性、安全、回归、遗漏测试和范围漂移；
- 给出 `PASS`、`PASS_WITH_RISKS` 或 `FAIL`，并附证据。

不负责：

- 只根据执行线程摘要下结论；
- 为了让结果通过而降低验收标准；
- 在验证线程直接修复问题。发现问题后回到新的执行轮次。

## 3. 建立控制记录

主线程在委派前保留一份简短控制记录。它可以留在对话中，不必创建额外文件：

```yaml
goal: 一句话说明要达成的结果
baseline: 分支和提交 SHA，或“未提交工作树 + git status 摘要”
scope_in:
  - 允许修改或研究的内容
scope_out:
  - 明确不能触碰的内容
constraints:
  - 数据、权限、兼容性、时间或工具边界
acceptance:
  - 可观察且可复现的完成条件
writer: 当前唯一写入线程；无则为 none
candidate: 尚未冻结 | 提交 SHA | 精确 diff/文件集合
verification: 未开始 | 进行中 | PASS | PASS_WITH_RISKS | FAIL
open_decisions:
  - 仍需主线程或用户决定的问题
```

基线检查至少包括：当前目录、适用规则、`git status --short --branch`、相关代码或文档的真实状态。工作树不干净时先区分已有改动与本任务改动，不得擅自覆盖。若任务明确不提交，用 `git diff --binary` 记录已跟踪文件基线，并记录未跟踪文件列表；对本任务新增且需要交付的未跟踪文件，在候选冻结时记录路径、大小和 SHA-256，避免只凭聊天摘要判断版本。

## 4. 完整执行顺序

### 阶段 A：冻结任务简报

主线程把模糊需求转成可交付简报：

1. 目标是什么；
2. 哪些内容在范围内和范围外；
3. 必须遵守哪些边界；
4. 用什么证据判断完成；
5. 遇到什么情况必须停止并回报。

验收标准应描述行为或可观察结果，例如“特定输入返回 404 且测试覆盖该分支”，而不是“代码写得更好”。

### 阶段 B：安排读取与写入

- 代码定位、资料核对、测试设计、日志归类等互不依赖的只读任务可以并行。
- 同一工作树中的实现任务默认串行，只指定一个 `delivery_executor` 写入。
- 确实需要多个写入者时，每个写入者使用独立 worktree、互斥文件范围和明确的集成负责人；合并前仍要统一验证。
- 主线程等待会影响下一步决策的结果，不要让无人消费的代理继续运行。

### 阶段 C：执行并回传证据

执行线程先确认简报，再实施、检查并返回结构化结果。主线程收到结果后：

1. 对照范围检查是否有漂移；
2. 查看真实 diff 或冻结提交，不只看总结；
3. 确认测试命令、退出状态和未运行项；
4. 将候选状态冻结为提交 SHA；若不提交，则保存完整 tracked diff，并为新增交付文件记录路径、大小和 SHA-256；
5. 释放写入者，再启动独立验证。

### 阶段 D：独立验证

验证线程只拿到完成判断所需的信息：原始目标、执行报告、当前文件或产物状态、验收标准、候选基线、允许的检查和已知环境限制。执行者的解释可以作为线索，但不能代替检查。

验证至少覆盖：

- 改动是否解决原始目标；
- 是否触碰范围外内容或破坏数据边界；
- 主要失败路径和边界条件；
- 测试是否真正覆盖行为，而不只是匹配文案；
- 文档、配置和实现是否一致；
- 是否存在未披露的手工步骤或环境依赖。

“只读验证”是指不得修改源码、候选产物、配置、Git 状态或外部数据。只有在任务简报明确允许且运行环境支持时，验证可把一次性缓存、数据库或测试输出写到隔离的系统临时目录，并在结束时报告位置；优先使用禁止字节码/缓存的选项和合成夹具。若测试必然写入候选工作树或只读沙箱不允许临时写入，验证者不得绕过限制，应把该检查列为未运行，并独立审查执行线程的原始测试证据。

### 阶段 E：修复回路

验证为 `FAIL` 时，主线程把每个可复现发现转成新的执行简报；验证线程不直接修改。修复后重新冻结候选并复验受影响区域。

在不改变范围的前提下，最多自动进行两轮“修复 → 复验”。同一阻塞连续出现两次、需要改变验收标准、需要新权限或需要范围外改动时，停止循环并交回主线程或用户决定。

### 阶段 F：最终验收

三线程路径中，主线程只有在以下条件满足时才宣布完成；快速路径则由主线程用同一验收标准完成直接自检：

- 候选状态和改动范围明确；
- 必需检查已通过，未运行项有原因；
- `FAIL` 发现已关闭，`PASS_WITH_RISKS` 风险已被接受或清楚披露；
- 用户已有工作未被覆盖；
- 没有仍在运行且会改变结果的线程。

只有主线程或用户能在其现有权限内接受 `PASS_WITH_RISKS`。范围外副作用、数据或权限边界破坏、用户工作丢失、敏感信息暴露和未满足的硬性验收标准必须修复或取得新的明确授权，不能仅披露后通过。

## 5. 交接模板

### 主线程 → 执行线程

```markdown
角色：你是本轮唯一写入者。
目标：<可观察结果>
基线：<工作目录、分支、SHA、工作树状态>
范围内：<文件、模块、行为>
范围外：<明确禁止项>
约束：<权限、数据、兼容性、用户已有改动>
验收标准：
- <条件 1>
- <条件 2>
必须运行：<检查；无法运行时必须说明>
停止条件：<需要新决定、权限、范围外改动或发现冲突>
回传格式：状态、改动文件、实现摘要、命令与结果、证据、假设、风险、待决定项。
```

### 执行线程 → 主线程

```markdown
状态：COMPLETE | PARTIAL | BLOCKED
改动：<文件与行为摘要>
验证：<精确命令、退出状态、关键结果>
证据：<diff、文件位置、截图或可复现步骤>
未运行：<检查与原因>
假设/风险：<明确区分已观察事实与推断>
范围偏差：无 | <说明>
需要主线程决定：无 | <问题>
```

### 主线程 → 验证线程

```markdown
角色：只读独立验证；不要修复。
原始目标：<不要改写为执行者的方案>
验收标准：<逐条列出>
候选：<提交 SHA 或精确 diff/文件集合>
基线：<比较对象>
重点风险：<需要特别检查但不预设结论的区域>
允许的检查：<命令、浏览器或静态审查边界>
回传格式：结论、逐条验收结果、发现、复现证据、未验证项、残余风险。
```

### 验证线程 → 主线程

```markdown
结论：PASS | PASS_WITH_RISKS | FAIL
验收结果：
- [通过/失败/未验证] <标准与证据>
发现：<按严重度排序；没有则写“无”>
复现：<命令、路径、输入和实际结果>
未验证：<内容与原因>
残余风险：<即使通过仍需知道的风险>
```

### 主线程最终交付

```markdown
结果：<完成了什么>
改动：<关键文件或提交>
验证：<已通过的检查和独立结论>
未验证/残余风险：<无则明确写无>
后续：<仅列真正需要的下一步>
```

## 6. 证据标准

优先级从高到低：

1. 可复现的行为结果、测试退出状态、精确 diff 或冻结提交；
2. 文件和符号位置、配置值、新文件哈希、截图或生成物；
3. 工具输出的短摘要；
4. 推断和解释。

报告必须把“观察到”与“推断出”分开。只回传关键错误和统计，不复制整段日志；需要保留长日志时给出本地路径或工件引用。

## 7. 常见失败与处理

- **主线程被日志淹没**：让执行线程只回传摘要、退出状态和证据位置。
- **两个线程同时改同一文件**：立即停止新增写入，保留双方状态，由主线程决定串行重做或隔离合并；禁止用破坏性 Git 命令解决。
- **执行者顺手扩大范围**：候选不得进入验证，通过新简报明确接受或撤回范围外改动。
- **验证者顺手修复**：撤销验证角色的写入权限，另开执行轮次。
- **测试环境缺失**：记录具体缺口，运行可行的替代检查，但不得把替代检查表述为完整通过。
- **新权限或外部副作用出现**：停止并取得明确授权；原任务授权不能自动扩大。
- **同一问题反复出现**：达到两轮上限后报告根因、尝试过的证据和需要的决定，不继续盲目重试。

## 8. 本仓库约束

- 只在 `D:\Development\Projects\game-wiki` 写入。
- `E:\Games\GameTools` 是只读外部数据源；不得修改、移动、删除或整库复制。
- 测试默认使用合成夹具和系统临时目录，不用真实外部资料证明写入安全；必要时通过 mock/spy 或明确的只读打开方式验证代码没有外部写路径，并披露机械隔离的局限。
- 不提交凭据、个人信息、私有数据或大型生成物；日志和样例先脱敏。
- 行为变化配套相称测试；保留用户已有改动。
- 未经用户明确要求，不提交、推送、建分支或改写 Git 历史。
